## 1. Product objective and exact boundary

Add an original **Files** application for safe browsing and bounded text preview **inside the unprivileged desktop user's home directory**. The tested guest remains the x86-64 QEMU/TCG 1024×768, two-vCPU, 2-GiB, OVMF/GRUB/ext4 Debian trixie image with the repository-built kernel, unprivileged UID/GID 1000 Sway/DRM/Pixman session, GTK3, Gio and the existing original P3.1 top bar, launcher and Dock. This is an additional client application, not a new compositor, kernel, installer or privileged file-management service.

**In scope:** a distinct 720×520 GTK3 window; original dark styling; Back, Home and Refresh controls; a search/filter entry; Show hidden toggle; a scrolled, deterministically ordered directory listing; navigation within ordinary readable home subdirectories; regular-file UTF-8 preview bounded at 65,536 bytes; clear blocked/unavailable states; integration with the real guest application launcher and Sway window list/Dock.

**Deliberately out of scope:** file creation, rename, delete, copy or move; drag-and-drop mutation; opening or executing external programs; following symbolic links; mounting/unmounting, network shares, removable media, privileged directories outside the home, arbitrary URI handling, file associations, binary/image/media/PDF preview, thumbnailers, search indexing, trash, Finder/macOS compatibility, a settings suite, notifications, production accessibility certification, crash recovery, bare-metal hardware and an installer. Such features need separate threat models and acceptance contracts.

## 3. Filesystem and UI safety invariants

1. **Local home confinement.** `SafeHome` is the sole authority for directory traversal and preview. Start at the UID-1000 user's actual home, use directory-file-descriptor-relative `os.open` with `O_NOFOLLOW`, validate each component and never trust a label, search result, `..`, absolute path, free-form URI or symlink target as authority. Reject traversal outside the authorized home even under path replacement/races.
2. **No symlink dereference.** Symlink entries may be shown clearly as blocked, but must not be navigated or previewed, including links pointing to `/etc/os-release`, links within home, loops or links swapped during a click. Reject regular-file race substitutions, devices, FIFOs, sockets and other special objects.
3. **Deterministic bounds.** Display at most **256** directory entries at once, with deterministic sorting, safe display of hostile Unicode/markup-like filenames, explicit truncation/limit state, and no unbounded recursion or background crawling. Search filtering and Show hidden must operate on the same safe bounded listing.
4. **Preview bound.** Read only a regular, authorized UTF-8 text file, display at most **65,536 bytes**, and refuse oversized, non-UTF-8/binary or unsafe content with a clear 'Preview unavailable' state. Do not interpret file bytes as Pango markup, HTML, a command or a `.desktop` executable. A denied read may not leak contents through preview, logs or an error dialog.
5. **Application read-only policy.** Files itself performs no guest filesystem mutations, subprocess/shell invocation, mount or privilege elevation. Never inject a host directory/mount into the test guest. Test-only challenge files may be created through a **separate, real QMP-driven unprivileged Terminal**; such fixture writes are not Files functionality. Offline read-only verification of a *copy* of the guest disk artifact after shutdown is permitted. The ordinary desktop account has no sudo access.
6. **Genuine UI.** Back/Home/Refresh, search, Show hidden, directory activation and file selection must act through mapped GTK widgets and preserve focus/navigation state. An app-emitted 'success' line is a clue to verify, never a substitute for actual on-disk content, Sway state, HID acknowledgments and QMP framebuffer pixels.

## 4. Required native-QEMU qualification scenario (future gate)

This section is a **required acceptance design**, not a claim that a P3.2 QMP harness already exists or passed. The first `.github/workflows/phase3-files.yml` integration may establish clean installation and P3.1 regression only; until the following independent UI oracle and verifier are executable and green, P3.2 remains **NOT QUALIFIED**.

1. **Clean build/boot and challenge.** Check out one exact clean source SHA. Build the own kernel and distinct Phase 3 UEFI disk from signed inputs. Start real QEMU TCG with virtio DRM/KMS/keyboard/tablet, Sway/Pixman and UID-1000 seat. Capture an initial QMP scanout and generate a fresh unpredictable hexadecimal nonce **after** readiness. Through genuine QMP keyboard input to a real `foot` session, create a regular UTF-8 challenge file under `~/Documents/p32-<nonce>/proof-<nonce>.txt` containing that same nonce, plus controlled negative fixtures such as a symlink to `/etc/os-release`, an oversized file and a binary file. Bound guest commands to the generated hexadecimal fixture names; never supply a host directory or mount.
2. **Launch through the desktop.** Open the existing GTK launcher through QMP pointer, search for **Files** through its mapped search entry and activate the source-installed Gio `.desktop` result by real keyboard/pointer input. Independently observe a distinct live `org.phase3.Files` Sway surface and PID under UID 1000, its actual mapped geometry consistent with the source-defined 720×520 client (accounting only for documented compositor decoration/gaps), and a changed actual QMP GPU framebuffer. A source `set_default_size` call, host-spawned process or shell-generated marker cannot qualify.
3. **Navigate and preview.** Use QMP clicks on source-derived, actually mapped directory/file row coordinates to enter the nonce directory, navigate Back/Home and return, exercise search and Show hidden, then preview the genuine challenge file. Require independent on-disk nonce/content verification, bounded UI acknowledgments, a visible preview of matching text, ordered Sway/GTK events and distinct PPM/PNG screenshots for each meaningful transition. Reject stale/fabricated hitboxes, screenshots or IPC.
4. **Negative controls.** In the same live Files session, use QMP to select actual listed symlink, oversized/binary and special entries, and require visible denied/unavailable states with no outside-home read, unintended launch or **mutation of the challenge file**. The Files UI has **no arbitrary path or URI entry**: exercise `..`, absolute paths, untrusted URIs, symlink swaps and traversal races through host `SafeHome` API adversarial tests instead of inventing a GUI path-entry action. Independently run missing-GPU and Files-start-failure controls; they must fail inside the guest with no healthy Files UI claim, not merely from a host launch timeout.
5. **Two-boot persistence.** Cleanly power down, reboot the same persistent test overlay, launch Files again using genuine HID and confirm the challenge file still has the identical nonce bytes, the app remains read-only, the source-owned Files window truly maps and all core safety tests still pass. Require bounded QEMU exit and inspect the guest filesystem rather than trusting an application printout.
6. **Hash-bound verifier.** Preserve actual QMP JSONL replies to HID/screendump and powerdown, raw GPU PPMs and lossless PNG previews, Sway `get_tree` projections, guest process/UID evidence, serial logs, negative-control logs, signed package inventory, manifest/build hashes and test-results. A standalone source-bound verifier must replay scenario state and screenshot/nonce integrity, reject missing or forged evidence and mark failed diagnostic bundles `not_validated`.

**Regression and repeat requirement:** On the **same final P3.2 source SHA**, independently complete successful Phase 1, Phase 2 and *full* P3.1 workflows without weakening their accepted oracles, and **two complete independent fresh-runner P3.2 qualification runs/attempts**, each with all positive and negative native-QEMU scenarios, verifier success and distinct reviewable SHA256-bound artifacts. Host tests, packaging-only jobs or one green native attempt are insufficient. Preserve qualifying evidence beyond GitHub Actions' short artifact retention; do not edit the tested commit solely to flip these rows to DONE.

## 6. CI staging, reviewer procedure and exclusions

- The independent first-pass workflow is `.github/workflows/phase3-files.yml`. It runs a clean source-SHA-bound **P3.1 native QEMU regression** and `distro/phase3/ci/files-package-check.sh` against the four actual installed Files source/mode/root-UID identities. It collects `logs/files-package-identity.json` and an explicit `logs/files-qualification.json` with `status: not_validated`, and its artifact name contains `UNQUALIFIED`. **This is packaging/regression integration only—not native Files UI acceptance.** The future full Files QMP test and standalone verifier remain design obligations until implemented; a green first-pass workflow leaves **every P32 row PENDING**.
- On the eventual full workflow, verify clean checkout/source SHA, deterministic signed dependencies, installed-file/desktop-entry hashes, 16 acceptance rows, exact QMP actions and framebuffer sequence, raw serial/process/PID/UID/IPC data, negative cases, clean shutdown and hash-bound artifact identity. Collect diagnostics even on failure without treating them as qualified.
- Distinguish test fixture writes through an ordinary guest Terminal from application writes. A malicious symlink escape, path race, denied preview, crash or unclean QEMU exit must fail the run rather than be explained away by a green host check.
- Report the scope honestly: a read-only **home** file browser on an emulated QEMU target. Do not imply general-purpose file management, systemwide filesystem privileges, file associations, thumbnails, real hardware, macOS compatibility or installer readiness.
